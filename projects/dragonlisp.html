LANGUAGE MODEL AND TYPE SYSTEM

DragonLisp is an experimental Lisp dialect implemented in Java and designed to execute on the Java Virtual Machine. Its default language model is dynamically typed: ordinary functions, bindings, and expressions do not require static type annotations. Optional declarations may provide additional information to the compiler for checking or specialization, but the absence of a declaration must not make a valid program uncompilable. This distinction is fundamental to the project: DragonLisp is intended to retain the flexibility of a Lisp while taking advantage of the JVM as an execution platform.

READER, SYNTAX, AND SEMANTIC ANALYSIS

Compilation begins by reading Lisp syntax into structured forms, preserving distinctions among symbols, literals, lists, and nested expressions. A subsequent analysis stage identifies bindings, function calls, special forms, and lexical scope, and reports malformed input before bytecode generation. Clear source locations and diagnostics are important because an error in a nested form should not surface merely as an opaque JVM failure. Decisions about namespaces, quoting, macro expansion, and evaluation order belong to the language specification and must be made consistently across interpreted or compiled execution paths.

DIRECT JVM BYTECODE COMPILATION

The compiler is designed to emit JVM class files and instructions directly, rather than translating Lisp programs into Java source code first. Expression compilation must respect the JVM operand stack, local-variable slots, branch targets, method descriptors, and object representations. Conditional forms, calls, returns, and nested scopes must lower into control flow that satisfies bytecode verification. The generated classes must be valid for the targeted JVM and load correctly through standard class-loading mechanisms. Direct emission gives the project control over its runtime representation, but it also makes verifier correctness and instruction-level testing central engineering concerns.

DYNAMIC VALUES AND OPTIONAL OPTIMIZATION

A dynamic Lisp value may represent numbers, strings, symbols, collections, functions, or user-defined objects, and the runtime needs consistent rules for how those values move through generated methods. Optional type information can support specialized operations or reduce boxing where the compiler can prove that doing so preserves program behavior. When such proof is unavailable, compilation must retain the dynamic path rather than silently imposing a static restriction. Type mismatch reporting, numeric behavior, function arity, and interoperability conversions should be deliberate language rules, not accidental consequences of Java casts.

RUNTIME SERVICES, JAVA INTEROP, AND VALIDATION

Beyond generating instructions, DragonLisp requires runtime services for function invocation, closures, environments, symbol resolution, and language-level errors. Running on the JVM also creates opportunities for calling Java classes, though method resolution and conversion between Lisp and Java values need explicit interfaces. Validation should cover reader edge cases, lexical scoping, recursion, branching, optional declarations, generated class loading, and equivalence between expected semantics and actual execution. The project is under independent development; these architectural descriptions express technical direction and do not imply that every runtime or compiler feature is complete.
