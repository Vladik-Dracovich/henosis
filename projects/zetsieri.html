EDITOR MODEL AND DESIGN

Zetsieri is a minimalist Common Lisp development editor organized around two persistent working surfaces: a source editor and an adjacent SBCL read–eval–print loop. Rather than treating evaluation as a separate terminal task, the interface places the running Lisp image beside the text being developed. The design emphasizes immediate feedback, a small number of visible controls, and a predictable path from editing a form to evaluating it. This is a Lisp-focused workspace, not an attempt to replicate every feature of a general-purpose IDE.

VIM-STYLE MODAL INPUT

Keyboard interaction follows a Vim-inspired distinction between command/navigation and text insertion. The input layer interprets keystrokes in the current mode before forwarding editing operations to the buffer. Cursor movement, insertion, deletion, and mode changes are therefore separate concerns from drawing text on screen. Keeping that boundary explicit is important for avoiding state inconsistencies when the cursor moves across lines, text is modified, or a key sequence is interrupted. The goal is familiar modal editing without forcing the REPL to inherit the editor’s keybindings.

BUFFERS, FILES, AND EVALUATION

A file opened in Zetsieri becomes an editable buffer; it does not automatically become part of the running SBCL image. Lisp definitions are made available to the runtime by evaluating forms or explicitly loading a source file. This distinction matters when a function appears correctly in the editor but SBCL reports it as undefined. A reliable evaluation workflow must account for package context, read errors, compilation or load failures, and the difference between a form’s returned value and text printed as a side effect. Buffer state and runtime state should remain independently understandable.

REPL OUTPUT AND ERROR REPORTING

The right-hand REPL is intended to handle both short interactive expressions and substantial streams of output, with a scrollable transcript that does not overwrite earlier results. It should distinguish submitted input, printed output, returned values, and diagnostic messages, particularly when a condition interrupts evaluation. Package-qualified symbols, undefined functions, and missing external dependencies are common Lisp development problems that benefit from visible, specific error feedback. Programs that create separate graphics windows or rely on third-party systems must still load their own dependencies into SBCL; the editor itself does not implicitly provide those facilities.

IMPLEMENTATION BOUNDARIES AND EXTENSIBILITY

Zetsieri’s architecture can be separated into a text-buffer model, modal command dispatcher, file operations, view/layout renderer, and SBCL evaluation interface. Those boundaries make it easier to test editing behavior independently of process communication or window drawing, and to add commands without rewriting the entire interface. Because Common Lisp supports incremental development and runtime redefinition, the longer-term direction is a workspace that can evolve through Lisp code while remaining lightweight. Documentation describes the intended design and development behavior; individual capabilities should be confirmed against the version being run.
